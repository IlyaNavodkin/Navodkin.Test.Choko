# Design

## Context

См. proposal.md. Приложение — NW.js с Node в renderer'е (`lib/node.ts`), fs-слой `services/repo-fs.ts` с self-write, store-slice'ы и прогоны-папки `.casewright/runs/<stem>/` (снапшоты `itemText/checks/failNotes`). Внешний `node` нужен отдельно: `process.execPath` в NW.js указывает на бинарник NW.js, а не на Node, поэтому runner запускает системный Node.

## Goals / Non-Goals

**Goals:** тестировщик пишет тесты в VS Code как обычно; приложение показывает их, связывает с кейсами, запускает с нужным окружением из прогона и сохраняет проверяемый результат, не затрагивая ручные данные прогонов.

**Non-Goals:** установка зависимостей, запуск кода при открытии репозитория, скрытое исполнение при импорте отчёта, sandbox чужого кода, собственный test runner.

## Решение по запуску: официальные репортеры Playwright

Запуск выполняет сам Playwright CLI проекта, а не self-made раннер:

1. **Раннер.** Приложение (Node в renderer'е) разрешает CLI проекта через `createRequire(<repo>/package.json).resolve('@playwright/test/cli')`, спавнит **внешний node** с argv-массивом (`shell: false`), `cwd` репозитория и подготовленным окружением. Путь к Node ищется в PATH, при неудаче — явный путь в настройках приложения; версия проверяется против требований установленного в проекте Playwright. Ни `npx`, ни `npm install`, ни скачивание браузеров приложение не выполняет.
2. **Источник истины по статусу — официальный JSON-отчёт.** Каждый запуск получает уникальный выходной каталог исполнения; Playwright пишет туда JSON (`--reporter=json`, `PLAYWRIGHT_JSON_OUTPUT_NAME`), ассеты — в `--output`. Терминальное состояние определяется связкой «exit code + наличие и валидность отчёта + correlation по каталогу исполнения»: exit 0 без валидного отчёта — это `runner_error`, а не успех; exit ≠ 0 при unexpected-статусах — это упавшие проверки, а не ошибка раннера. Статусы `expected/unexpected/flaky/skipped`, attempts, retries, ошибки и вложения берутся из отчёта, а не из парсинга stdout.
3. **Версии.** Парсер отчёта объявляет поддерживаемый диапазон версий Playwright, определяет фактическую версию CLI и при выходе за диапазон показывает понятную диагностику вместо тихой ошибки; формат читается терпимо, лишние поля не роняют разбор.
4. **Прогресс.** JSON пишется в конце, поэтому промежуточный прогресс берётся из stdout официального `line`-репортера и каталога `--output` — **только для отображения** (см. «Наблюдаемость исполнения»). Сводка и статус никогда не вычисляются из прогресса.
5. **Выбор точного набора.** Identity теста — annotations `testoritto.caseId`, `testoritto.automationId`, `testoritto.variantId`, но CLI фильтрует по тегам/названию, а не по annotations. Поэтому контракт теста включает уникальный фильтруемый тег (`tag: ['@tt:<automationId>']`), а запуск использует `--project` + точный `--grep` с anchors; там, где версия Playwright поддерживает список тестов (`--test-list`), предпочитать его вместо grep. Отсутствие тега, дубликат ключа или неоднозначное совпадение — диагностика до старта, без «догадки по названию».
6. **Канал аргументов.** Аргументы передаются переменными окружения по ключу (`TESTORITTO_ARG_<KEY>`), типы приводятся по объявлению. Это работает и при ручном запуске теста в VS Code — значение берётся из `process.env` с дефолтом в коде, поэтому тест остаётся обычным Playwright-тестом без обязательного импорта нашего модуля. JSON-файл аргументов в репозиторий не пишется; секреты в аргументах не поддерживаются.
7. **Остановка.** Windows — завершение дерева процессов через `taskkill /T /F` по PID (spawn без shell) либо Job Object; macOS — процесс-группа (`detached`) и `process.kill(-pid)`. При закрытии репозитория, приложения или по таймауту дерево завершается; незавершённые попытки помечаются `interrupted`, прежние попытки сохраняются. Корректность проверяется на каждой ОС.
8. **Импорт остаётся отдельным путём.** Для отчётов из CI или ручных прогонов приложение разбирает Playwright JSON и JUnit терпимым parser'ом с preview matched/unmatched/duplicate и идемпотентным применением. Импорт ничего не исполняет.

### Наблюдаемость исполнения

У execution явная машина состояний, и каждый переход опирается на проверяемый сигнал, а не на догадку:

| Состояние | Сигнал |
|---|---|
| `queued` | пользователь нажал Start, процесс ещё не запущен |
| `starting` | процесс заспавнен; Playwright загружает config и поднимает workers |
| `running` | первая содержательная строка `line`-репортера («Running N tests…») или первый завершённый тест |
| `finishing` | процесс завершился, идёт разбор отчёта |
| `completed` | exit code + валидный отчёт + разобранные результаты |
| `runner_error` | процесс завершился без валидного отчёта, config не загрузился, отчёт не соответствует выбору |
| `cancelled` | пользователь остановил запуск |
| `interrupted` | процесс или приложение оборвалось; после переоткрытия stale-running переводится в `interrupted` |

- **Старт.** «Запустилось» — это факт спавна процесса; «тесты реально выполняются» — первая строка `line`-репортера или первый завершённый тест. Если за порог нет ни строк, ни выхода — диагностика «config долго не стартует» с хвостом логов, а не бесконечный спиннер.
- **Прогресс.** Всего тестов известно из выбранного набора; завершённые считаются по строкам `line`-репортера (деградация до «выполняется» + логи, если строки не парсятся), показываются прошедшее время, текущий invocation и bounded хвост логов. Прогресс не влияет на итог.
- **Liveness.** Отсутствие вывода дольше порога показывает предупреждение «возможно, завис», но процесс не убивается до таймаута.
- **Завершение.** Результат разбирается из отчёта и маппится на привязки по annotations discovery (fallback — file+title из discovery); статусы, attempts, длительность и вложения сохраняются; UI показывает тост и бейдж на строке прогона; execution остаётся доступным после переоткрытия. `test-results/.last-run.json` и `stats` отчёта используются как вторичная проверка.
- **Точные события шагов** (`onTestBegin`) даёт только собственный reporter — это вариант 2/3, отложенный до момента, когда базового прогресса не хватит.

### Порядок, группировка и параллелизм

«Последовательность» распадается на три разных вещи, и приложение отвечает только за две:

1. **Порядок и параллелизм внутри одного запуска Playwright** определяются конфигурацией проекта (`workers`, `fullyParallel`, `test.describe.serial`, dependency projects). Приложение их не переупорядочивает и не форсирует `--workers=1`: иначе локальный результат перестанет совпадать с CI. Строгий порядок тестов — ответственность теста (serial/один тест), а не настройка приложения.
2. **Группировка выбранного набора в invocation'ы.** Тесты с одинаковым разрешённым набором аргументов и project выполняются одним процессом (меньше старта браузеров), тесты с другими аргументами — отдельными invocation'ами. По умолчанию группировка включена; режим «один тест на invocation» доступен как более изолированный, но более медленный.
3. **Порядок invocation'ов** детерминирован: порядок строк прогона / порядок выбора, последовательно. Параллельный запуск нескольких групп — настройка на будущее, не поведение по умолчанию.

Перед запуском UI показывает состав каждой группы, зависимости проектов (auth setup и подобные — Playwright выполнит их сам) и предупреждает, если какие-то тесты будут выполнены Playwright'ом параллельно.

### Альтернативы и почему отклонены

| Вариант | Оценка |
|---|---|
| Свой bundled reporter + bridge-процесс | Даёт события в реальном времени и полный контроль над форматом, но наш код исполняется внутри процесса теста, растёт связность с версией Playwright и усложняется диагностика. Отложено как точечное улучшение прогресса. |
| Запуск через Node-API внутри NW.js | Runner Playwright — CLI, а Node внутри NW.js зафиксирован его сборкой; запуск браузеров из renderer-процесса хрупок. Отклонено. |
| Встроить Node в дистрибутив | Не снимает главную зависимость (Playwright всё равно ставится в проект), добавляет десятки МБ и платформенные бинарники. Отклонено. |
| Только импорт, без запуска | Не выполняет требование «запустить из прогона»; остаётся вспомогательным путём. |

## Остальные решения

1. **Контракт теста.**
   ```ts
   test('login works', {
     tag: ['@tt:login'],
     annotation: [
       { type: 'testoritto.caseId', description: '<stable case id>' },
       { type: 'testoritto.automationId', description: 'login' },
       { type: 'testoritto.variantId', description: 'valid-user' },
     ],
   }, async ({ page }) => {
     const baseUrl = process.env.TESTORITTO_ARG_BASE_URL ?? 'http://localhost:3000';
     /* ... */
   });
   ```
   Ключ — tuple `[caseId, automationId, project, variantId]` (`default` при отсутствии). Отсутствующий/дублирующийся ключ или тег блокирует запуск с диагностикой.
2. **Хранилище.** `.testoritto/automation/catalog.json` (автотесты), `bindings.json`, `profiles.json` — машинные данные с детерминированной сериализацией; executions — `.testoritto/automation/executions/<executionId>/` (manifest, report, логи, вложения). Результаты, сохранённые в прогон, кладутся в `<run>/automation/<executionId>/` как sidecar'ы, которые загрузчик прогонов игнорирует (он читает только `_run.md` и `*.md`).
3. **Доверие.** Discovery и запуск — только по явному действию для доверенного профиля (cwd, config, projects, timeout, retries, workers). Профиль хранится в app-data; изменение конфигурации отзывает доверие. Пользователь явно предупреждается, что config и тестовый код исполняются с его правами без sandbox.
4. **Аргументы.** Автотест объявляет определения аргументов (тип, required, default, enum, min/max). Значения разрешаются с приоритетом `schema default → autotest → binding → run override`; значением может быть литерал или ссылка на ключ записи «Аргументы» справочника (`entryId`, `key`). Перед запуском показывается preview итоговых значений и источников; снимок (resolved value + revision) сохраняется в execution и в отчёт. Архивная/изменённая/отсутствующая запись — ошибка до старта.
5. **Запуск из прогона.** Один тест с двумя наборами аргументов даёт два invocation с разными id. Автоматический результат показывается отдельно от ручного и не перезаписывает checks/notes/снапшоты; «применить к сводке» — явное действие с проверкой revision. Повтор упавших — новый execution с `parentExecutionId`.
6. **Отчёты.** PDF/JSON-отчёт прогона получает раздел автотестов: статус, длительность, attempts, вложения; отдельная таблица «аргументы и источники» с именем набора окружения. Вложения блокируемых типов (HTML) не открываются и не исполняются.
7. **Идентичность кейсов.** Привязка ссылается на стабильный `id` кейса; переименование/перенос связь не меняет; удалённый кейс показывает unavailable, история попыток сохраняется.
8. **Пределы.** Отчёт/import ограничены по размеру и числу тестов, логи агрегируются с усечением, вложения ограничены по размеру и типу; превышение — fail-closed с диагностикой.

## Risks / Trade-offs

- Исполнение чужого config/test code с правами пользователя — не sandbox; это явное требование доверия в UI.
- Требование внешнего Node/Playwright — осознанная цена; отсутствие диагностируется, ничего не устанавливается молча.
- Прогресс по stdout-репортеру менее надёжен, чем события своего reporter; поэтому он только отображение, а истина — отчёт.
- Выбор по тегу требует дисциплины в тестах; отсутствие тега блокирует запуск с понятным сообщением, а не тихо запускает лишнее.
- JSON-каталоги в Git конфликтуют при параллельной правке; детерминированная сериализация и мелкие файлы снижают риск.

## Migration Plan

Порядок: раннер+JSON-отчёт → discovery/selection → каталог/привязки/аргументы → интеграция в прогон → отчёты → импорт → приёмка. Существующие репозитории не меняются до первой явной привязки; откат — удаление `.testoritto/automation` и run-sidecar'ов automation.
