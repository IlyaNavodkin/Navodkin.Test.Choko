# Spec Delta

## Purpose

Общий справочник репозитория хранит определения, сокращения и ссылки на документы, позволяет использовать их в кейсах и сохранять смысл исторических прогонов.

## ADDED Requirements

### Requirement: Repository reference catalog
Система SHALL предоставлять записи типов term, abbreviation и document с неизменяемым ID, названием, описанием, альтернативными названиями, необязательным HTTP(S) URL и признаком архива. Название обязательно; хотя бы описание или URL SHALL быть заполнено.

#### Scenario: Create and edit entry
- **WHEN** пользователь создаёт валидную запись и явно сохраняет её, затем изменяет название
- **THEN** запись доступна в каталоге, а её ID не меняется

#### Scenario: Invalid entry
- **WHEN** название пусто, отсутствуют и описание и URL либо URL небезопасен/некорректен
- **THEN** система показывает ошибку поля, удерживает черновик и не заменяет сохранённую запись

### Requirement: Find and archive entries
Система SHALL искать по названию, альтернативным названиям и описанию, фильтровать по типу и архиву. Архивация SHALL сохранять ID и содержание; архивные записи не предлагаются для новых связей по умолчанию.

#### Scenario: Find abbreviation by meaning
- **WHEN** пользователь ищет полное название сокращения и выбирает фильтр abbreviation
- **THEN** каталог показывает подходящие записи; отсутствие совпадений показывает empty state со сбросом фильтра

#### Scenario: Archive and restore
- **WHEN** пользователь архивирует запись, затем находит её в архиве и восстанавливает
- **THEN** её ID и содержимое сохранены, а запись вновь доступна в активном каталоге

### Requirement: Explicit save and draft protection
Система SHALL разделять черновик и сохранённую запись, защищать черновик при выборе другой записи, создании новой, навигации, смене репозитория и закрытии. Ошибка записи SHALL удерживать черновик; заблокированный репозиторий SHALL запрещать изменения.

#### Scenario: Leave dirty entry
- **WHEN** пользователь переходит из изменённой записи
- **THEN** он может остаться, сохранить или отменить изменения до перехода

#### Scenario: Save failure
- **WHEN** запись не удалась или исходная версия изменилась извне
- **THEN** сохранённые данные не перезаписываются, черновик остаётся доступен для повторного решения

### Requirement: Portable stable references
Система SHALL вставлять из выбора справочника обычную Markdown-ссылку на файл записи со стабильным ID, показывать её пояснение и места использования. Переименование записи SHALL не переписывать автоматически кейсы. Неразрешённая ссылка SHALL оставаться читаемым текстом с диагностикой.

#### Scenario: Rename referenced entry
- **WHEN** название записи изменилось после вставки ссылки в кейс
- **THEN** ссылка разрешается по прежнему ID; её сохранённый текст не переписывается без действия пользователя

#### Scenario: Missing reference
- **WHEN** связанный файл отсутствует или выходит за границу допустимого справочника
- **THEN** система показывает неразрешённую ссылку без чтения постороннего файла и без потери текста кейса

### Requirement: Reading and inserting glossary references
Система SHALL открывать кейс в режиме чтения с явным переходом к редактированию. Значение справочника в тексте SHALL открывать пояснение и переход к записи. Вставка SHALL выбирать активную запись поиском и сохранять ссылку в позиции курсора. Переключение режимов SHALL не сохранять и не сбрасывать черновик.

#### Scenario: Read a glossary value
- **WHEN** пользователь нажимает значение справочника в тексте кейса
- **THEN** открывается карточка пояснения с действием перехода к записи; кейс не становится изменённым

#### Scenario: Insert and read reference
- **WHEN** пользователь выбирает запись через «Из справочника» в редактируемой секции и переключается на чтение
- **THEN** значение вставлено в выбранную позицию и открывает карточку выбранной записи; несохранённый draft остаётся несохранённым

#### Scenario: Missing or archived value
- **WHEN** существующая ссылка указывает на отсутствующую либо архивную запись
- **THEN** отображается диагностика отсутствия либо архивное пояснение, а новые вставки архивной записи не предлагаются

### Requirement: Historical reference snapshots
Система SHALL фиксировать доступные пояснения, названия и URL использованных записей при создании прогона и читать их из snapshot. Неисправные ссылки SHALL диагностироваться до создания; продолжение с неполным набором пояснений требует явного решения пользователя.

#### Scenario: Definition changes after run creation
- **WHEN** запись отредактирована или архивирована после создания прогона
- **THEN** исторический прогон показывает прежнее пояснение и не обращается к текущей записи для его подмены

#### Scenario: Incomplete reference set
- **WHEN** выбранный кейс содержит неразрешённую ссылку
- **THEN** создание прогона показывает проблему и не скрывает отсутствие пояснения

### Requirement: Compatible local storage
Система SHALL хранить справочник отдельными читаемыми Markdown-файлами вне существующего формата кейсов Casewright. Открытие репозитория SHALL не создавать каталогов или миграций. Запись SHALL проверять session, canonical scope и revision, сохранять неизвестное содержимое и использовать очередь операций.

#### Scenario: Open existing Casewright repository
- **WHEN** открывается репозиторий без справочника
- **THEN** его байты и структура остаются неизменными, а справочник показывает пустое состояние

#### Scenario: Stale or unsupported document
- **WHEN** документ изменён извне или его версия не поддерживается
- **THEN** запись отклоняется с диагностикой без потери исходного файла

### Requirement: Safe external documents
Система SHALL открывать проверенный HTTP(S) URL только по явному действию пользователя через native API. Описание SHALL не выполнять HTML, скрипты или автоматическую загрузку внешнего документа.

#### Scenario: Read entry offline
- **WHEN** пользователь читает сохранённое описание без сети
- **THEN** описание доступно, а внешний URL не запрашивается автоматически

#### Scenario: Unsafe URL
- **WHEN** входные данные содержат javascript, file или другой неподдерживаемый протокол
- **THEN** он не становится активной внешней ссылкой и не выполняется

### Requirement: Honest prototype boundary
Изолированный веб-прототип SHALL явно обозначать хранение в памяти, не выполнять IPC/fs/Git/внешние запросы и не объявлять файловую интеграцию готовой. Состояние разных демо-репозиториев SHALL быть изолировано.

#### Scenario: Reload prototype
- **WHEN** пользователь перезагружает UX preview после сохранения записи
- **THEN** данные возвращаются к fixtures согласно видимому предупреждению о демо-хранении

#### Scenario: Switch demo repository
- **WHEN** пользователь сохраняет запись в одном демо-репозитории и открывает другой
- **THEN** запись первого не появляется в каталоге второго

### Requirement: Structured environments for automation
Система SHALL поддерживать записи справочника типа environment с именем, описанием и уникальными типизированными несекретными values; обычный Markdown не интерпретируется как конфигурация. Выбор аргумента SHALL ссылаться на entry ID/key и сохранять immutable resolved snapshot в invocation.

#### Scenario: Reusable environment values
- **WHEN** пользователь создаёт prod/stage с host/baseUrl и выбирает значение в аргументе
- **THEN** показаны ключ, тип и итоговое значение; ошибочный тип/дубликат keys/архивная запись блокируют новый выбор

#### Scenario: History survives edits
- **WHEN** значение окружения изменяется после execution
- **THEN** новые запуски требуют актуального preview, старые результаты сохраняют прежнее resolved value/source revision; существующие term/document записи не меняются
