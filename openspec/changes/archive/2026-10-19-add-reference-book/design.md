# Design

## Context

См. proposal.md. Текущее приложение читает и пишет `.ch/` (`services/repo-load.ts`, `services/repo-fs.ts`), кейсы сериализует `services/format/case.ts`, все записи помечает self-write (`markWrite`) и debounce-ит (`services/persist.ts`). `utils/markdown.tsx` рендерит inline-разметку, `utils/markdown-html.ts` — HTML для PDF-отчётов; относительные ссылки сейчас отображаются текстом (`safeUrl` пропускает только http/https/mailto). Точки расширения — эти сервисы и store-slice'ы.

## Goals / Non-Goals

**Goals:** каталог записей с двумя видами сущностей, стабильная Markdown-ссылка, читаемая без приложения, снапшоты в прогоне и источник значений для аргументов автотестов.

**Non-Goals:** секреты в значениях, произвольные относительные пути за пределы `.testoritto/glossary` текущего репозитория, автозамена слов, облачная синхронизация, изменение формата кейсов и `.ch/`.

## Decisions

1. **Одна сущность-запись, два вида.** Общий конверт `kind: link | arguments`, а не два независимых каталога: единый поиск, архив, ссылки и UI. Вид определяет только набор полей, идентичность всегда `id` (uuid). Совпадение названий допустимо.
2. **Файл на запись.** `.testoritto/glossary/<uuid>.md`; front matter `schema_version: 1`, `id`, `kind`, `title`, `aliases`, `archived`, для `link` — `url`, для `arguments` — `values` (в YAML-виде). Тело — Markdown-описание. Файл на запись даёт короткие Git-диффы и читаемость без приложения; имя файла не зависит от названия, поэтому переименование не двигает файлы и не ломает ссылки.
3. **Валидация.** `title` непустое; хотя бы `description` или `url` заполнены; `url` — только корректный HTTP(S) без credentials; у `arguments` ключи уникальны, тип значения — из фиксированного набора, `enum` требует непустой список. Пароли/токены хранить запрещено — это документированное ограничение, UI показывает предупреждение.
4. **Вставка — обычный Markdown.** В текст вставляется `[Название](относительный/путь/.testoritto/glossary/<uuid>.md)`, путь вычисляется от файла кейса. Resolver считает ссылку валидной только если канонический путь ведёт внутрь `.testoritto/glossary` текущего репозитория; иначе ссылка остаётся текстом с диагностикой. Ссылки внутри code-блоков не считаются использованием.
5. **Чтение ссылки.** В режиме чтения/предпросмотра ссылка показывает название и открывает карточку записи (описание, URL, переход в раздел), не изменяя кейс. Архивная запись читается старой ссылкой, но не предлагается для новых вставок.
6. **Перемещение кейса/съюта.** Операция move в `cases-slice.ts` пересчитывает относительные пути распознанных ссылок (справочник и изображения из change `add-rich-text-and-images`) в той же операции; нетронутый текст ссылки сохраняется.
7. **Снапшоты прогона.** При создании прогона собираются использованные `link`-записи и, если пользователь выбрал набор, `arguments`-запись. Снапшот (`id`, `revision` = sha256 исходного файла, `title`, `url`, `description`, resolved values) пишется в папку прогона как extension-sidecar (`glossary.json`, `arguments.json`). Загрузчик прогонов читает только `_run.md` и `*.md`-sidecar'ы (`repo-load.ts:loadRuns`), поэтому JSON-файлы остаются для него невидимыми и существующие прогоны не меняются. Неразрешённая ссылка диагностируется до создания прогона; создание с неполным снапшотом требует явного решения. Конкретизация формата, лимитов и правил чтения — раздел «Run snapshot v1».
8. **Выбор набора аргументов.** Прогон может быть создан без набора (по умолчанию) или с выбранным `arguments`-набором; для автотестов набор выбирается на экране запуска (`add-playwright-automation`). Изменение записи после прогона не переписывает снапшот; новый запуск использует новую revision.
9. **Открытие без записи.** Отсутствие `.testoritto/` — нормальное состояние пустого каталога; каталог создаётся только первым явным сохранением. Атомарная запись (temp + rename) и self-write-маркировка — как в `repo-fs.ts`.

## Storage format v1 (конкретизация решения 2)

Файл `.testoritto/glossary/<id>.md` — YAML front matter + тело-описание. Порядок ключей фиксирован; строковые скаляры квотируются, если иначе прочитались бы как число/boolean/пустая строка.

```yaml
---
schema_version: 1
id: 0f8fad5b-d9cb-469f-a165-70867728950e   # = имя файла
kind: link                                   # link | arguments
title: Payments runbook
aliases: [payments, PSP]
archived: false
url: https://example.com/payments            # только link, необязателен
values:                                      # только arguments
  - key: retries
    type: number                             # string | number | boolean | url | enum
    value: 3
  - key: env
    type: enum
    value: dev
    options: [dev, stage]                    # только enum, непустой и без повторов
---
Markdown-описание.
```

Правила чтения (fail-closed: сомнительный файл не перезаписывается):

- `id` берётся из имени файла; расходящееся поле `id` — предупреждение и самоисправление при следующем сохранении.
- Скаляры (`title`, `url`, строковые значения, элементы `aliases`) приводятся к строке — это потеря не данных, а только типа.
- Неизвестные поля front matter (включая payload «чужого» вида) сохраняются как есть и перевыпускаются в JSON-flow-форме — валидный YAML, точно переживающий round-trip любой структуры.
- Перевод строки файла сохраняется при сохранении (LF по умолчанию для новых записей); CRLF нормализуется только для разбора.
- Read-only (показывается с диагностикой, никогда не перезаписывается): невалидный YAML, неизвестный `kind`, `schema_version` больше текущего, неверный тип `archived`, `aliases` не список, а также структурные проблемы `values` (не список, строка без типа, неизвестный тип, значение не своего типа, `options` не список).
- Семантические правила (пустой `title`, нет ни описания, ни URL, дубли ключей, небезопасный URL) — ошибки сохранения с подсветкой поля: черновик удерживается, файл не заменяется.

## Run snapshot v1 (конкретизация решения 7)

Папка прогона `.ch/runs/<stem>/` получает два необязательных extension-sidecar'а; оба пишутся один раз при создании прогона и никогда не перезаписываются приложением (это история, а не настройки).

`glossary.json`:

```json
{
  "schema_version": 1,
  "entries": [
    { "id": "0f8f…", "revision": "sha256 байтов файла записи", "kind": "link",
      "title": "Payments runbook", "description": "…", "url": "https://…", "archived": false }
  ],
  "unresolved": [ { "id": "…", "where": "AR-0001 — Step 3", "reason": "there is no record file for this link" } ]
}
```

`arguments.json` (только если набор выбран):

```json
{ "schema_version": 1, "id": "…", "revision": "sha256", "title": "dev", "description": "…",
  "values": [ { "key": "retries", "type": "number", "value": 3 }, { "key": "env", "type": "enum", "value": "dev", "options": ["dev", "stage"] } ] }
```

Что и откуда берётся:

- Использованные записи — из текста кейсов прогона (Objective, Systems, Setup name/body, Steps, Acceptance), code-aware тем же сканом, что и при перемещении; дубликат ссылки даёт одну запись, `where` — первое место.
- Ревизия читается с диска в момент создания (`readGlossaryEntry`), а не из загруженного каталога — иначе можно зафиксировать устаревшую ревизию.
- Выбранный набор `arguments` — необязательный (`null` = прогон без значений; отсутствие выбора ничего не блокирует).

Fail-closed:

- Ссылка, которую нельзя зафиксировать (нет файла, запись read-only, семантически невалидная запись, описание длиннее лимита, превышен лимит числа записей), попадает в `unresolved` и **показывается до записи**; прогон создаётся только после явного решения пользователя («Create the run without them»), и `unresolved` остаётся в файле — отсутствие пояснения не скрывается.
- Выбранный набор `arguments`, который нельзя зафиксировать (нет файла, read-only, не тот вид, архивный, невалидные значения/дубли ключей, слишком много значений), **блокирует** создание прогона — автотесты читают значения по ревизии, и прогон, «заявивший» набор, которого не захватил, был бы хуже отсутствия прогона.
- Лимиты (`RUN_SNAPSHOT_LIMITS`): 200 записей, 20 000 символов описания, 200 значений. Усечения нет — превышение диагностируется как unresolved.
- Пустой снапшот (нет записей, нет unresolved, нет набора) не пишет ни одного файла: у прогона без ссылок папка остаётся ровно такой, как раньше.

Чтение:

- Загрузчик строк прогона по-прежнему определяет их только по `_run.md` и `NNN-*.md`; `glossary.json`/`arguments.json` читаются отдельно и только как снапшот (в `Run.snapshot`). Отсутствующий, повреждённый или частично нечитаемый файл — предупреждение и прогон без замороженных определений, никогда не ошибка загрузки; строки и порядок из `.order` от JSON не зависят.
- Пока открыт прогон (вид `run`/`guide`), чипы ссылок резолвятся снапшотом раньше живого каталога: прогон показывает прежние название и пояснение, даже если запись изменена, заархивирована или удалена. Ссылки, которых в снапшоте нет (дописаны в текст прогона позже), резолвятся живым каталогом. Под модальным окном (правка живого текста) снапшот не действует.
- `Duplicate` переносит снапшот исходного прогона как есть: копия описывает те же определения, и повторная заморозка по сегодняшнему справочнику молча переписала бы историю.

## Risks / Trade-offs

- Новый формат → versioned parser и round-trip fixtures до включения writer'а; неизвестные поля и виды записей не перезаписываются.
- JSON-снапшоты внутри папки прогона — расширение её формата: загрузчик их игнорирует, но при удалении/переименовании прогона снапшот может остаться «сиротой» — диагностика, не падение.
- Ссылки живут в Markdown как обычные ссылки → возможны ручные правки; resolver обязан отклонять выход за границу справочника, а не «открывать что попросят».
- Снапшот увеличивает объём прогона → ограничение на размер описания и число записей (fail-closed с диагностикой).

## Migration Plan

Никакой миграции при открытии. Порядок: схемы+парсер → fs-сервис → UI каталога → ссылки в тексте → снапшоты прогона → interop с аргументами автотестов. Откат — удаление `.testoritto/glossary`; файлы кейсов и прогонов остаются читаемыми без приложения.
